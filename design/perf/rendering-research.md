# Rendering performance research (three.js r186, WebGPU + WebGL 2 fallback)

Date: 2026-10-06. Research only; nothing here has been run in our lab unless it says "ours".
Method: four parallel research passes against three.js r186 source/PRs/issues (dev tree package 0.186.0, r187 in development), MDN, caniuse, web3dsurvey, vendor docs. Every claim marked UNVERIFIED could not be confirmed in source or a measurement; "estimated" means reasoning, not measurement.

Our measured baseline (from the brief): render bundles 9-21x on static separate meshes; InstancedMesh per kind; BatchedMesh in WebGPU still one draw per object; static sun shadow via `shadow.autoUpdate=false`; casters limited to big objects; log depth holds 4 km free; GTAO at 2x DPR = 90% of a frame (4 fps, RX 460); Lambert < Standard < Physical cost; Godot web is Compatibility-renderer only.

## 0. Findings that change plans (read first)

1. **Bundles freeze culling.** Children of a `BundleGroup` are frustum-culled and `LOD.update()`d only when the bundle is (re)recorded; afterwards the contents are fixed. The official `webgpu_performance_renderbundle` sets `frustumCulled=false` on children. So: bundles suit coarse units (one per room/cell) toggled by `.visible`, not fine culling or LOD inside one bundle. Bundles are cached per camera, so shadow cameras record their own.
2. **The WebGL 2 fallback has no render bundles** (`WebGLBackend` has no `beginBundle`; BundleGroup degrades to a plain Group). The 9-21x gain vanishes on every phone that falls back. Roughly one in five iPhones (iOS < 26 / pre-A13) and Android devices without Vulkan 1.1 take that path. Plan phone budgets as if bundles do not exist, and bench both paths.
3. **Tiled lighting is gone; clustered lighting replaced it.** `TiledLighting` (r170) was removed in r185 (PR #33751); `ClusteredLighting` (r185, PR #33406) is WebGPU-only and clusters only non-shadow PointLights. `DynamicLighting` (r184, PR #33042) is the cross-backend option.
4. **r186 has `SSAONode`** (PR #33921), claimed about 2x cheaper than GTAO at matched resolution, defaulting to half resolution, no temporal pass needed. And `GTAONode` has `resolutionScale`. Our 90% GTAO cost was most likely scale 1, 16 samples, 2x DPR.
5. **Upscalers exist in core since r184:** `FSR1Node` and `TAAUNode`, plus `PassNode.setResolutionScale()` which shrinks only the scene render target (canvas and output stay full size).
6. **MSAA store flags (r186, PR #33974):** `storeMultisampledColorBuffer/Depth/Stencil` default to `true`, which the PR itself calls potentially expensive on tiled GPUs. Set them false on phones so the resolve stays in tile memory.
7. **BatchedMesh on WebGPU is not batched**: one `drawIndexed` per visible item (PR #30645, indirect version, open draft, slower on Chrome macOS until culling is on compute; issues #29580, #31935 open). Multi-draw-indirect still needs `chrome://flags/#enable-unsafe-webgpu` (checked 2026-10-05 via a third-party tracker; not in Chrome 155/156 by default). Treat as unavailable on phones.
8. **Light churn leaks (#34705, r186, closed 2026-09-29):** removed/disposed lights are never GC'd (NodeBuilder binding-group cache), with shadow cameras too. Pool candle lights; do not add/remove.
9. **InstancedMesh2 (`@three.ez/instanced-mesh`) is WebGL-only**; WebGPU support is a WIP PR (agargaro/instanced-mesh #154/#161). No ready-made LOD/culling library exists for 100k trees on WebGPURenderer; we build it (clusters, or compute culling + indirect).

## 1. Culling

### 1.1 GPU-driven compute frustum / Hi-Z culling
- three has no built-in GPU culling or Hi-Z as of r186. Building blocks exist: `IndirectStorageBufferAttribute` (r170), `geometry.setIndirect(attr, offset | offset[])`. In `WebGPUBackend._draw`, an array of offsets yields one `drawIndexedIndirect` per offset from a single buffer (poor man's multi-draw).
- Recipe: a TSL `Fn(...).compute(N)` tests each instance bounding sphere against frustum planes (uniforms), writes surviving indices to a storage buffer, `atomicAdd`s `instanceCount` in the indirect args; vertex stage reads the instance matrix through the index. Template: `examples/webgpu_struct_drawindirect.html` (5 x u32 draw struct written by compute, `renderer.compute(init)` then `renderer.compute(fill)`). `indirect-first-instance` is optional but ~99.98% overall / 99.75% Android of WebGPU devices (web3dsurvey; not cross-checked), feature-detect anyway.
- Hi-Z: no public three.js implementation found. Non-three reference: "Shade" WebGPU engine does HZB occlusion plus GPU frustum and small-primitive culling (https://discourse.threejs.org/t/shade-webgpu-graphics/66969?page=3). "ComputeBatchCulling" in three.js Blocks: docs URL 404, UNVERIFIED availability.
- Cheap CPU stand-in with measured benefit: split a monolithic InstancedMesh into ~20 spatial clusters: 3x fps through frustum culling (forum, procedural forest, https://discourse.threejs.org/t/procedural-instanced-forest-high-performance-real-trees/88610). Core InstancedMesh is culled only as a whole by its bounding sphere.
- Phones: compute is WebGPU-only (no WebGL 2 path). For our 100k trees the WebGL fallback needs the cluster approach regardless.

### 1.2 Occlusion queries
- `object.occlusionTest = true` + `renderer.isOccluded(object)`, since r156 (PR #26335), both backends, unchanged in r186. Example `webgpu_occlusion.html`. Each flagged object's draw is wrapped in a query; results resolve at pass end via `mapAsync`, so they arrive 1+ frames late (read from code, not measured).
- Only drawn objects get queried: if you hide an object because it was occluded it stops being tested. Pattern: a cheap proxy box (`colorWrite=false`, `depthWrite=false`, `occlusionTest=true`) per room/door/large group; toggle real content from the proxy result; re-show on doubt; accept one frame of pop-in. Occluders must be drawn first (renderOrder).
- Occlusion queries cannot be recorded inside render bundles per the WebGPU spec (no `beginOcclusionQuery` on `GPURenderBundleEncoder`); proxies must sit outside any `BundleGroup`. Spec reading, three.js behaviour untested.

### 1.3 Portals / cells for interiors
- Nothing in three core or addons (GitHub "portal" repos are stencil see-through, not visibility). Forum advice: group by room, toggle visibility (https://discourse.threejs.org/t/the-most-efficient-way-to-display-heavy-environments/39362).
- Suggested (our own design): one `BundleGroup` per room plus doorway quads; each frame start from the camera's room, project portal quads to screen, clip to the current screen rect, recurse into the neighbour if non-empty (2-3 levels); set `room.visible`. CPU-only, microseconds at ~30 rooms, works on both backends. Cheaper variant: precomputed visible-room sets + door open/closed state. `object.visible=false` returns before the children are walked (verified in `_projectObject`), so hiding a room root is the cheapest cull. Fits bundles perfectly (finding 0.1).

### 1.4 Distance / visibility ranges, LOD
- `THREE.LOD`: `addLevel(obj, distance, hysteresis)`; autoUpdate runs inside the renderer scene walk. No separate "visibility range"; use an empty last LOD level, `camera.far`, or layers. `webgl_batch_lod_bvh` (`@three.ez/batched-mesh-extensions`) is WebGL-oriented.

### 1.5 Multi-draw-indirect and BatchedMesh
See finding 0.7. Effect: on WebGPU, one InstancedMesh per kind (plus compute culling writing `instanceCount`) beats BatchedMesh. A BatchedMesh inside a BundleGroup would cut CPU encode cost, but its per-frame culling/sorting stops once recorded (UNVERIFIED in practice).

## 2. Lighting

### 2.1 Many candles
- **ClusteredLighting** (r185+): `renderer.lighting = new ClusteredLighting(maxLights=1024, tileSize=32, zSlices=24, maxLightsPerCluster=64)` from `three/addons/lighting/ClusteredLighting.js`. Forward+ clustered; compute bins light spheres into 32 px tiles x 24 exponential slices. `PointLight.distance` must be set (cull radius). Lights depth-sorted on CPU each frame. Example `webgpu_lights_clustered`.
  - Numbers (PR comments): ~120 fps with 1000 lights on M2 Pro; example default 700. No phone numbers: UNVERIFIED on mobile.
  - Caveats: shadow-casting, spot, directional lights fall back to the per-light path; WebGPU only; resize rebuilds the grid (stutter reported); 64 lights per cluster.
- **DynamicLighting** (r184): `renderer.lighting = new DynamicLighting({ maxPointLights: 64 })` packs non-shadow lights into uniform arrays; changing light count no longer recompiles materials. Loops all lights, no culling; both backends. Probably right for tens of candles per room.
- **Per-material lights:** `material.lightsNode = lights([a, b])` (`webgpu_lights_selective`) restricts a material to a room's candles; cuts shader loop cost without clustering.
- **Renderer-level:** `renderer.lighting = new Lighting subclass`. r186 PR #34622 replaced the `addLight/addClass` registry with per-light `lightNode`; `addLight` deprecated.
- Candle glow: emissive flame mesh + additive halo sprite is cheapest (see 3.4).

### 2.2 Baked lighting vs real-time
- Lightmaps: `material.lightMap` (uv1) works in node materials (`webgpu_materials_lightmap`). Offline bake (Blender) is the quality path for candle-lit panelling; `ProgressiveLightMapGPU` can bake in-browser (needs UV2 unwrap).
- **LightProbeGrid** (WebGPU r185; WebGL2 variant r184, PR #33125): `new LightProbeGrid(w,h,d,nx,ny,nz)`, `grid.bake(renderer, scene, {cubemapSize:8, sampleCount:512, bounces, start, count})`, then `scene.add(grid)`; L2 SH irradiance on all lit node materials, GPU bake, no readback, incremental via `start/count`. Examples `webgpu_lightprobes{,_complex,_sponza}`. Caveat: trilinear blend, no visibility term, so light leaks through walls: one grid per room. Bake time UNVERIFIED.
- **VXGI** (r186, PR #34402): voxel cone tracing GI + AO, WebGPU only, static geometry, described as expensive. Not for phones.
- Static manor + flickering candles: bake ambient/indirect (probes/lightmaps/AO), keep only candle direct light real-time and mostly unshadowed.

### 2.3 Shadows
- r186: `PCFSoftShadowMap` deprecated/removed (#33987). PCF is 5 Vogel-disk taps with IGN noise and hardware compare (#32381); `shadow.radius` widens the disk without extra taps (constant cost). VSM adds two separable blur passes per update; not for point lights. Basic = single tap.
- Caching: `ShadowNode.updateBefore` renders only if `shadow.needsUpdate || shadow.autoUpdate`; `autoUpdate=false` + one `needsUpdate=true` works for all light types including point (matches our static sun result).
- Point lights (`PointShadowNode`): 6 scene renders into a `CubeDepthTexture` per update, then 5-tap cube PCF. A static candle with autoUpdate=false pays the six passes once. Cheaper: intensity-only flicker needs no shadow update; bake candle occlusion; contact/blob shadows (`webgpu_shadow_contact`: depth-from-above blurred plane, costs an extra pass); real shadows for only the nearest 1-2 candles.
- CSM: `light.shadow.shadowNode = new CSMShadowNode(light,{cascades:3,maxFar,mode:'practical',lightMargin,fade})` (WebGPU only; `webgpu_shadowmap_csm`). r186 `SunLight` addon (PR #34326): two fitted cascades in one atlas; docs say not for single rooms. `TileShadowNode` (r175+) for large areas. Exteriors will want CSM or a static sun map + big casters.
- No published per-technique timings for WebGPU found: measure.

## 3. Anti-aliasing and post

### 3.1 AA options
- Baseline: with tone mapping/sRGB on, plain `render()` already draws to an offscreen half-float buffer then an output pass copies to screen (`needsFrameBufferTarget`). `new WebGPURenderer({outputBufferType: THREE.UnsignedByteType})` halves that buffer's bandwidth but loses HDR headroom for bloom (reasoning, not measured).
- **MSAA:** WebGPU allows 1 or 4 samples only. `antialias:true` -> `renderer.samples=4`; a `pass()` target takes it unless `options.samples` given. Cheapest on tiled GPUs if the resolve stays in tile memory (set the store flags false, finding 0.6; https://github.com/mrdoob/three.js/pull/33974). Does not smooth shader aliasing or alpha-test; use `material.alphaToCoverage=true` for tree leaves. Must be off for TRAA/TAAU.
- **Conflict to resolve on device:** one pass says three r186 already uses `TRANSIENT_ATTACHMENT` (Chrome 146+) for discarded MSAA attachments (`WebGPUTextureUtils.js`); another reads PR #33946 comments as "three doesn't use it". UNVERIFIED; check the source in the lab.
- **FXAANode:** one full-screen pass, cheapest post AA; needs sRGB input (`fxaa(renderOutput(scenePass))`); blurs fine detail (window lattice, text).
- **SMAANode:** 3 passes (edges, weights, blend) on half-float targets; est. 2-3x FXAA (estimated).
- **SSAAPassNode:** N scene renders; not for phones.
- **TRAANode:** needs velocity MRT, half-float history, depth history copies, 3x3 neighbourhood clip, Halton jitter via `setViewOffset`. Velocity covers instanced/batched/skinned (previous-frame matrices doubled in memory). Ghosting open (issue #31892); history resets on resize (fights `setPixelRatio` scaling); transparent/additive objects (flames) have no velocity and smear unless drawn after. No published cost.
- **Phone default (recommendation):** MSAA 4x with store flags off; FXAA if post is already running; TRAA as desktop quality option.

### 3.2 Ambient occlusion
- `GTAONode` `ao(depth, normal, camera)`: `resolutionScale` (default 1), `samples` (16; changing recompiles), `useTemporalFiltering`; r186 added blue noise + AO-channel accumulation (PR #33663); r186 example runs 0.5 scale + temporal + TRAA. Below scale 1 it is noisy without temporal filter or `DenoiseNode`. Applied via `scenePass.contextNode = builtinAOContext(aoTex.sample(screenUV).r)`: darkens indirect/ambient only.
- **SSAONode** (r186, PR #33921): Vogel-disk, one depth tap per sample, separable depth-aware blur, default scale 0.5, no TAA needed, example pairs with MSAA 4x. Claimed ~2x cheaper than GTAO at matched resolution/samples (PR GPU timestamps). Needs a normal MRT. Reversed-depth support only in r187 (#34790): relevant to our "reversed partial" log-depth finding. Our estimate (not measured): SSAO at 0.5 with 8-16 samples ~ 1/8 of our measured GTAO.
- n8ao-webgpu 0.1.0 (Apr 2026, three ^0.182), community TSL port, `halfRes` with depth-aware upsample, claims 2-4x; WebGPU only. https://github.com/marioandf/n8ao-webgpu
- **Candle-lit caveat:** screen-space AO darkens only the ambient term; in a candle room most light is direct, so payoff may be small. Look before paying. Baked AO (`aoMap`, uv1 lightmaps, vertex colours, baked into tree textures) is free at runtime and suits static interiors; blob shadows under furniture are nearly free.

### 3.3 Dynamic resolution and upscaling
- Two knobs: `renderer.setPixelRatio()` reallocates the canvas and all targets (forum: black frames, oscillation; https://discourse.threejs.org/t/changing-pixelratio-based-on-fps-good-or-bad-idea/34563). `scenePass.setResolutionScale(s)` (PassNode, r181+) shrinks only the scene target; still reallocates via `renderTarget.setSize`, so use quantized steps (0.5/0.625/0.75/0.875/1), not continuous.
- Controller (drei `PerformanceMonitor` defaults, verified): average fps over 250 ms windows, collect 10 averages, act when 75% fall outside bounds ([40,60] at 60 Hz; [60,100] above 100 Hz), step 0.1, fall back to a fixed value after N flip-flops. Add hysteresis: drop fast, rise slowly, after a rise check 3-20 frames and revert if unhelpful. Only pays when fill-rate bound; our many-object rooms may be CPU/draw-bound, so confirm first.
- GPU timing: `new WebGPURenderer({trackTimestamp:true})` (needs `timestamp-query`), `await renderer.resolveTimestampsAsync(THREE.TimestampQuery.RENDER)` -> last frame GPU ms, arrives a frame or more late. web3dsurvey: 98.8% of WebGPU devices (Android 97.9%, iOS 100%, Safari 93%); Chrome rounds to 100 us. Per-pass accuracy on tile GPUs: UNVERIFIED. WebGL 2 fallback: `EXT_disjoint_timer_query_webgl2` on only 0.23% Android / 0.22% iOS, so use rAF frame time (it only shows when over budget). `Inspector` addon shows per-pass timings in development.
- **FSR1Node** (r184, PR #33339): EASU + RCAS; `fsr1(scenePass, 0.2)` with `scenePass.setResolutionScale(0.5)`; docs say use only when fragment-bound and feed it an anti-aliased input (MSAA on the low-res pass).
- **TAAUNode + SharpenNode** (r184, PR #33368): temporal, 9-tap Blackman-Harris; MSAA off; blurrier/more flicker than TAA on thin features (window leading); same velocity/transparency caveats; https://github.com/mrdoob/three.js/pull/33368 and https://github.com/mrdoob/three.js/issues/33359.
- `SharpenNode` = RCAS alone, one cheap pass. `@pmndrs/upscaler` (FSR 2/3 port, WGSL compute, WebGPU only, no MSAA input, no perf numbers; heavy for phones).
- Realistic phone path: 0.5-0.75 scale + MSAA, then FSR1 or bilinear + RCAS. Desktop may try TAAU.

### 3.4 Tone mapping, bloom, candle glow
- Tone mapping is free inside the existing output pass.
- `BloomNode`: 0.5 resolution scale by default; bright pass + 5-level mip chain of separable Gaussians (kernels 6/10/14/18/22) + composite, ~12 passes per frame, half-float. Phone cost UNVERIFIED but bandwidth/pass-count dominated on tilers. Selective bloom adds an MRT attachment.
- ARM (Bjorge, SIGGRAPH 2015): dual-filtering (Kawase-style down/up) used ~7% of the bandwidth of linear-sampled Gaussian on a Mali-T760; three has no node for it, we would write one in TSL.
- Phone candle glow: emissive flame + camera-facing additive halo sprite (`depthWrite:false`, depth-tested, clamp on-screen size). Reserve bloom for desktop or phones at 0.25-0.5 scale with fewer mips. Halos ghost under TRAA/TAAU unless drawn after the temporal pass.

## 4. Geometry

### 4.1 LOD and impostors
- **Octahedral impostors:** `agargaro/octahedral-impostor` (WebGL, WIP; demo 200k trees, 2048^2 atlas, no fps; author says cross-fade not needed with enough angular resolution; README not read, API UNVERIFIED); `ektogamat/octahedral-impostor-component` (WebGPU + TSL on `MeshBasicNodeMaterial`, 8/16/32-cell atlases, 4096 px demo, 3-frame barycentric blend = 3 samples/pixel, albedo only, demo not package; copy `src/impostor/`); Horde (TSL/WebGPU impostor crowds, reference). Discussion: https://discourse.threejs.org/t/a-forest-of-octahedral-impostors/85735
- **100k-tree LOD on WebGPU:** (a) CPU: one InstancedMesh per LOD level, re-bucketed per frame (https://github.com/Strange-tech/100kTrees); (b) GPU: compute writes visible IDs + instance count into an `IndirectStorageBufferAttribute` via `geometry.setIndirect`. `@three.ez/batched-mesh-extensions` has a WebGPU build with `addGeometryLOD` but inherits BatchedMesh's draw per object, and per-instance uniforms are WebGL-only.
- Forum forest findings: WebGPU default 8 vertex buffers per pipeline forced packing per-instance attributes (`InstancedInterleavedBuffer`); ~20 spatial clusters gave 3x; vertex-shader LOD collapses far leaves to `vec4(0,0,0,1)` so they are culled before fragment.
- Cross-fade: `material.alphaToCoverage` (needs MSAA); otherwise dither-discard with `hash(instanceIndex)` + screen coords; discard loses early-Z (keep band narrow); phone cost UNVERIFIED.

### 4.2 HLOD / merged city chunks
- No built-in HLOD. Practical: offline per chunk merge (gltf-transform `join`/`flatten`), simplify, bake one atlas, swap with `THREE.LOD`. `3DTilesRendererJS` provides streaming HLOD, core said to work with WebGPU but plugins break (issue #1380); partly UNVERIFIED.

### 4.3 Simplification
- `meshoptimizer` WASM (`MeshoptSimplifier`: `simplify`, `simplifyWithAttributes`, `simplifySloppy`; flags LockBorder, Prune, Permissive, Regularize, ErrorClamped); weld first (`mergeVertices`); you may rewrite only the index. Desktop speeds quoted (~20M tris/s sloppy, 28-50M tris/s full) are UNVERIFIED secondary; WASM and phones are slower. https://meshoptimizer.org/ , https://zeux.io/2025/09/30/billions-of-triangles-in-minutes/
- three `SimplifyModifier` reported poor on dense meshes. Recommendation: simplify offline (`gltfpack -si 0.25`, `-slb` lock borders; or gltf-transform `simplify`).

### 4.4 Compression, quantization
- `gltfpack -c/-cc` -> EXT_meshopt_compression (three: `GLTFLoader.setMeshoptDecoder` since r122): vertex data 2-4x smaller, indices ~1-1.2 B/tri, decode 3-6 GB/s desktop. gltfpack default quantization (UNVERIFIED exact: pos 14 bit, UV 12, normals 8). KHR_mesh_quantization: vertex 32-48 B -> ~20 B.
- r186 WebGPU (verified in source): snorm8/unorm8/snorm16/unorm16 and `Float16BufferAttribute` supported. **3-component 8/16-bit attributes are padded to x4 on the CPU at upload** (per-vertex copy loop; stored vertex 8 B not 6): store 4-component yourself.
- Octahedral normals: meshopt OCTAHEDRAL filter is decoded on CPU into normalized int8/int16 x4 normals; true oct-decode in shader needs a custom `normalNode`.

### 4.5 Phone triangle limits, small triangles
- No measured per-phone triangle budget found (only the rule of thumb "<100 draw calls, <100k vertices" from https://www.utsubo.com/blog/threejs-best-practices-100-tips, weak). Our own RX 460 "phone-shaped" numbers are the best data we have.
- 2x2 quad shading wastes up to 75% on 1-pixel triangles; below ~10x10 px triangles get much costlier ("40-80x for single-pixel geometry" is secondary, UNVERIFIED). Sources: https://blog.selfshadow.com/2012/11/12/counting-quads/ , https://www.g-truc.net/post-0662.html. Implication: book spines, mouldings and trees need LOD by screen size, not triangle count.

## 5. Materials and shaders

- **Compile cost** (issue #34386, Metal cold): JS node build 17 ms cold / 3 ms warm; GPU pipeline compile 180-400 ms each. Example 3 lights + shadows + env: nodes 10656 -> 5688, compile 404 -> 333 ms, fragment WGSL 16.5 -> 10.3 KB. Lever: fewer lights per material and fewer material configurations.
- **Shared node builds across InstancedMeshes** (PR #34776, split #34819/#34820): 1,200 InstancedMeshes: node builds 1,316 -> 142, pipeline compile ~30 s -> 5 s. #34819 still open at check time, targeted r187. Until then, fewer InstancedMesh objects per material.
- **TSL tips:** `.toVar()` to reuse, `.toConst()` for constants, `Fn(...).setLayout()` so helpers emit once, `.isolate()`; update uniforms only on change; never touch `material.needsUpdate` (recompiles); use `colorNode`/`positionNode` (`onBeforeCompile` does not apply to NodeMaterials); `addUpdateRange()` partial buffer uploads, `addLayerUpdate()` for array-texture layers. https://github.com/Makio64/advanced-threejs-tsl-webgpu-rendering
- **Pre-warm:** `renderer.compileAsync(scene, camera, targetScene?, onProgress?)` is non-blocking since r184; run behind the loading screen or when approaching a room. Bug (#34632, closed not planned): in r186 on many textured glTF materials with the loop running can throw "Binding doesn't exist" (yield mid-build while sampler state changes). Workaround: do not mutate texture sampler state during precompile, or pause the loop.
- **Precision:** no mediump in WGSL. r186 has `WGSLNodeBuilder.enableShaderF16()` and the `'shader-f16'` constant, but no caller in core: TSL does not emit f16 itself. f16 available for vertex attributes (`float16xN`), half-float render targets, `packHalf2x16`. Support: web3dsurvey 93.8% overall / 86% Android, but gpuweb #5006 says no Qualcomm Vulkan device qualifies (`uniformAndStorageBuffer16BitAccess`): contradictory, treat f16 as an optional path.
- **Material sharing:** one material per look = one pipeline, and makes bundles/instancing pay. r185/r186 notes: pipeline descriptor caching, InstancedMesh fully supported in render bundles (from a release-notes summary with garbled dates; check changelog).
- **Texture arrays:** `DataArrayTexture` / `CompressedArrayTexture`, `texture(arr, uv()).depth(layerNode)`; layer per instance via `instancedBufferAttribute(...)` or storage buffer + `instanceIndex`; all layers same size/format; default `maxTextureArrayLayers` 256. No library-grade virtual texturing found.
- **KTX2/Basis:** `KTX2Loader.detectSupport(renderer)` after `await renderer.init()` picks ASTC/BC7/BC1-3/ETC2. Stays compressed in VRAM: 2048^2 RGBA8 with mips ~21 MiB vs ~5.6 MiB at 8 bpp. WebGPU format support (web3dsurvey): ASTC 46.5% overall but 99.95% Android, 99% Safari; BC 87% overall, 35% Android; ETC2 46.7%. Without any (SwiftShader, compat mode) falls back to RGBA8.
- **Mipmaps/anisotropy:** keep mips for anything distant; anisotropy (clamped 16) on floors/panelling instead of more resolution; mobile cost unmeasured (UNVERIFIED), try 4 on phones.
- **Books:** InstancedMesh of a spine box per shelf cluster; per-instance attributes interleaved to stay under 8 vertex buffers: `vec4 rect` (atlas UV offset/scale), `vec4` packing colour/height/wear seed, layer index; `colorNode = texture(atlas, rect.xy + uv()*rect.zw)` mixed with procedural bands/lettering from `hash(instanceIndex)`. A shipped TSL example does exactly this; MyShelves warns a naive 4-box book costs ~19 draws (https://discourse.threejs.org/t/myshelves-a-first-person-library-you-build-book-by-book/93870). Distant shelves: bake a shelf to one card/impostor.
- Examples to read: `webgpu_performance_renderbundle`, `webgpu_instance_uniform`, `webgpu_mesh_batch`, `webgpu_loader_texture_ktx2`, `webgpu_loader_gltf_compressed`, `webgpu_materials_arrays`.

## 6. CPU side

- **`updateMatrixWorld`** always loops over every child; `matrixAutoUpdate=false` / `matrixWorldAutoUpdate=false` skip only the local matrix rebuild / world multiply, not the walk. Usage: static objects `updateMatrix()` once then `matrixAutoUpdate=false`; to skip the walk, `scene.matrixWorldAutoUpdate=false` and call `updateMatrixWorld()` on dynamic roots only (camera rig, doors, candles). Per-node cost est. 20-50 ns skipped / 100-200 ns composed: UNVERIFIED, add a lab case.
- **Per-object renderer cost** (`Renderer._projectObject`): every visible object visited per frame with `intersectsFrustum` for Mesh/Line/Points/Sprite when `frustumCulled`; centre transform per object when `sortObjects`; `renderList.sort` each frame (override with `setOpaqueSort/setTransparentSort`). Groups never frustum-tested. BundleGroup: children projected only at (re)record; a small per-frame refresh check remains. Open issue #30560 (high priority): 20k non-instanced cubes ~15 fps WebGPU vs ~60 WebGL on M1 Pro (uniform buffer per object -> many `setBindGroup`/`writeBuffer`); advice: instance/batch. https://github.com/mrdoob/three.js/issues/30560
- **Pooling/GC:** module-level scratch Vector3/Matrix4/Quaternion, no closures/spreads/`new` in the frame loop; pool lights (finding 0.8). Major GC pause lengths UNVERIFIED (minor scavenges usually <1 ms; major can take several ms: enough to drop a 60 Hz frame on a phone).
- **Worker + OffscreenCanvas:** WebGPU on OffscreenCanvas / `WorkerNavigator.gpu`: Chrome Android 121+, Safari/iOS 26+, Firefox 141+ (partial, Windows). rAF in workers: Chrome 69+, Safari 16.4+. three broke in workers in r179 (#31605), fixed in #31607. Only official worker example is WebGL (`webgl_worker_offscreencanvas`); no official WebGPU worker example. Usage: `canvas.transferControlToOffscreen()`, `new WebGPURenderer({canvas: offscreen})`, forward resize/DPR, `setSize(w,h,false)`; Pointer Lock/DOM events stay on main thread: batch `movementX/Y`, keys, touch by `postMessage` per frame (https://threejs.org/manual/en/offscreencanvas.html); loaders using `document`/`Image` need `ImageBitmapLoader`; CSS2D/HTML overlays do not work in the worker. Benefit is main-thread headroom and input latency, not GPU speed; on fill-bound/thermal phones it will not raise fps (UNVERIFIED for our workload).
- **Physics in a worker:** `@dimforge/rapier3d-compat` / `rapier3d-simd-compat` (embedded wasm loads in workers; simd 0.19.3 seen, a 0.20.0 version is UNVERIFIED); Dimforge reports 2-5x faster npm builds than 2024 (https://dimforge.com/blog/2026/01/09/the-year-2025-in-dimforge/). **No SharedArrayBuffer needed:** Rapier's JS build is single-threaded; use a transferable ping-pong (inputs + empty `Float32Array` out; worker steps, writes 7 floats per dynamic body, transfers back; render interpolates between last two states). Example https://codepen.io/foretoo/pen/ExeJqXX . If SAB is wanted on GitHub Pages (no COOP/COEP headers): `coi-serviceworker` (https://github.com/gzuidhof/coi-serviceworker): same-origin file, not bundled, reloads once on first visit, tries `credentialless` then `require-corp` (breaks cross-origin assets without CORP/CORS), fails in some embedded contexts. Our public site is on GitHub Pages, so default to the transferable approach.
- **Frame pacing:** iOS Safari rAF held near 60 Hz even on 120 Hz screens (Safari flag "Prefer Page Rendering Updates near 60fps" lifts it, on by default); Low Power Mode drops rAF to 30 fps undetectably (long-standing WebKit behaviour; recheck on iOS 26; https://popmotion.io/blog/20180104-when-ios-throttles-requestanimationframe/). Android Chrome follows panel rate (90/120 Hz). Use a fixed 60 Hz sim step with interpolated render; offer a 30 fps cap by skipping rAF callbacks from timestamps (not `setTimeout`); halves GPU energy roughly and delays throttling (direction established, size UNVERIFIED). `PressureObserver` (Compute Pressure API) is desktop Chrome 125+ only: no thermal signal on phones, adapt from measured frame time.

## 7. Phones

- **WebGPU availability (Oct 2026):** iOS/iPadOS/macOS Safari 26.0 shipped WebGPU on by default (https://webkit.org/blog/17333/webkit-features-in-safari-26-0/); caniuse lists iOS Safari 26.0-27.2 supported. iOS 26 needs iPhone 11 (A13) or newer (XS/XR dropped: widely reported, UNVERIFIED). iOS 26 adoption 66% of iPhones Feb 2026, 79% June 2026 (App Store data, 9to5mac): about one in five iPhones still gets WebGL 2. Android Chrome: on by default since 121 on Android 12+ with Qualcomm/ARM GPUs (https://developer.chrome.com/blog/new-in-webgpu-121); Chrome 146 (Feb 2026) shipped compatibility mode (WebGPU over OpenGL ES 3.1) starting with Android (https://developer.chrome.com/blog/new-in-webgpu-146). Chrome 139 cited 15% of Android users without Vulkan 1.1, 10% with no Vulkan. three r186 already requests `featureLevel: 'compatibility'` and sets `backend.compatibilityMode` if core features are missing; compat mode has extra restrictions (fewer storage buffers per stage, texture-view limits, maxTextureDimension2D 4096). Global caniuse 87.35% (85.72% full). Samsung Internet 24+ yes; Firefox Android off by default. "~78% of Chrome Android has WebGPU" and Imagination GPUs on Android 16: low-quality sources, UNVERIFIED.
- **Fallback:** `forceWebGL:true` forces WebGL 2; three falls back by itself without an adapter. On it: no BundleGroup, no compute (so no ClusteredLighting or GPU culling; which compute-based post nodes still work is UNVERIFIED, SSAO is fragment-only and should be fine), TSL translated to GLSL. Test both paths on real phones.
- **Thermal (3DMark Wild Life Extreme stress stability = worst/best):** iPhone 15 Pro 95.9%, iPhone 16 Pro 60.9% (Notebookcheck), iPhone 15 Pro Max throttles up to ~40% (Notebookcheck DE headline), Snapdragon 8 Gen 3 ~54% (Beebom), Pixel 8 ~52.5% (Notebookcheck; may be Wild Life not Extreme), Galaxy A55 98-99% (weaker but steady). Rule: budget about 50-60% of first-minute speed on flagships.
- **Pixel ratio:** iPhone 12-17 DPR 3: full canvas ~1170x2532 = ~3.0 Mpx; at DPR 1.5 ~0.74 Mpx (a quarter). Common practice: cap DPR at 2 desktop, 1.25-1.5 phone, plus the dynamic scaler. Matches our GTAO-at-2x result.
- **Tile-based GPU guidance:** Arm GPU Best Practices v3.4 (https://developer.arm.com/documentation/101897/0304): opaques front-to-back, transparents back-to-front; avoid `discard` in opaque shaders (forces late depth test); skip depth pre-pass (extra draws/bandwidth usually exceed overdraw saved; Mali-G725/Immortalis-G925 have hardware fragment prepass); watch blended layers per pixel. Apple (WWDC20 "Harness Apple GPUs with Metal", https://developer.apple.com/videos/play/wwdc2020/10602/): hidden-surface removal makes opaque order mostly irrelevant; `discard`/alpha-test disables it for those draws; order opaque, then alpha-tested (foliage), then blended; prefer alpha-to-coverage + MSAA over discard for leaves, test on device. Avoid: extra full-screen post passes (each writes the framebuffer out and reads back), mid-frame readbacks, render-target switches mid-pass, big blur chains, SSR, GTAO. Favour forward lighting with baked + few real-time lights.
- **Budgets:** no official mobile-web numbers. Nearest proxy Meta Quest (Adreno): Quest 2 <100 draws and <750k tris; Quest 3 <200 draws and <1.5M tris at 72 Hz, ASTC, no bloom/AO/SSR (https://developers.meta.com/horizon/resources/device-optimization-comparison/). Starting targets (UNVERIFIED, to confirm in lab): mid-range Android 100-200 draws, <500k-1M tris, DPR 1-1.25, 30-60 fps; iPhone 12-15 on WebGPU 200-500 draws (more with bundles), 1-2M tris, DPR 1.5.
- **Memory:** iOS has no fixed per-tab limit: min(WebKit memory-pressure limit, per-process kill limit); page silently reloads. Community-measured: ~1.5 GB iPhone 12 Pro, ~3 GB iPhone 15 Pro (UNVERIFIED, https://www.catchmetrics.io/blog/deep-dive-ram-internals-webkit); an older, more conservative anecdote puts the WebGL heap at 256-500 MB (UNVERIFIED for WebGPU). Plan ~256-500 MB of GPU resources on iPhone; ~500 MB-1 GB ceiling elsewhere (UNVERIFIED). `maxTextureDimension2D` defaults 8192 (4096 in compat mode); read `adapter.limits`. Use KTX2/ASTC. Safari can drop the context (`contextlost`) under pressure.
- **Battery:** 30 fps cap + DPR 1-1.5 is the biggest lever; render on demand when the view is still (forum reports static scenes "cooking" phones at full rAF); `powerPreference` is ignored on phones.

## 9. Ranked top 10 techniques to test next

Ranking weighs expected gain across both the manor and the later exteriors, cost to implement (S < 1 day, M 1-3 days, L > 3 days), and quality risk.

1. **Per-room BundleGroups + portal/visible-set room culling (manor).** Gain: large for interiors: bundles already 9-21x, and hiding whole rooms drops draw encode and vertex work for rooms not seen (expected 2-5x on multi-room scenes, estimated). Cost: M (room grouping, door-rect projection, rebuild policy, `frustumCulled=false` in bundles). Risk: low (a pop-in bug if portals are wrong; no visual change). Caveat: no benefit on the WebGL 2 fallback, where room toggling still helps but bundles do not exist.
2. **Phone render-scale controller + DPR cap + MSAA store flags off.** Gain: 1.5-4x GPU on fill-bound phones (pixel count scales with square of scale; est.); the store-flag change alone may save bandwidth on tilers (UNVERIFIED). Cost: S-M (`setResolutionScale` steps, timestamp-query with rAF fallback, hysteresis, optional FSR1/RCAS). Risk: low-medium (softness at low scale; mitigate with RCAS; reallocation hitches, so quantize steps).
3. **Candle lighting strategy bench: `DynamicLighting` vs `ClusteredLighting` vs per-room `lights([...])`, pooled lights, shadows autoUpdate=false.** Gain: removes shader-recompile hitches and per-fragment light loops; could be the difference between 10 and 60 candles on phones (estimated). Cost: M (three variants in the fps lab, measure on desktop + phone). Risk: low-medium (Clustered is WebGPU-only and covers only non-shadow point lights; need the cross-backend variant anyway).
4. **Baked indirect for the manor: per-room `LightProbeGrid` and/or Blender-baked lightmaps + baked AO, with SSAO/GTAO off on phones.** Gain: replaces the costliest post effect (90% frame) with ~0 runtime cost; probe sampling is one SH eval per fragment. Cost: M-L (bake pipeline, UV2, per-room grids; bake time UNVERIFIED). Risk: medium (light leaks in probes; flickering candles still real-time; baked data increases download).
5. **SSAONode at half resolution (r186) vs GTAO 0.5 + denoise, desktop quality tier.** Gain: est. 5-10x cheaper than our measured GTAO config (claimed 2x vs GTAO at matched settings, plus 4x from half res). Cost: S (swap node, normal MRT, MSAA 4x pairing). Risk: low-medium (darkens only ambient term: small visible payoff under candlelight; reversed-depth issue until r187).
6. **Forest pipeline: spatial InstancedMesh clusters (CPU) then compute frustum cull + `IndirectStorageBufferAttribute`, with LOD buckets.** Gain: cluster split alone 3x (forum) on 100k trees; compute culling and LOD reduce vertex load further (est. 2-5x more). Cost: M (clusters) to L (compute+indirect). Risk: low (visual identical); compute path is WebGPU-only, so keep clusters as the fallback.
7. **Octahedral impostors / cross-faded billboards for distant trees, and HLOD chunks for the city.** Gain: converts far trees from hundreds of tris to 2 (est. 5-20x vertex cost for the far field; also fixes small-triangle waste). Cost: L (bake atlas, adapt ektogamat TSL material, transition band, city chunk bake). Risk: medium-high (popping, lighting mismatch since impostors are albedo-only, silhouette quality).
8. **KTX2/ASTC (+BC7 desktop) texture pipeline, mip + anisotropy policy, texture-array atlas for books and furniture.** Gain: 4-8x less texture memory and bandwidth; the main protection against iOS tab reloads; fewer bindings. Cost: M (encode pipeline, `detectSupport`, fallbacks). Risk: low-medium (compression artefacts on gradient-heavy paint; ASTC only 46.5% of WebGPU devices overall, so ship both).
9. **Books: instanced spines with atlas + procedural shader, shelf-level impostors at distance.** Gain: thousands of books in a handful of draws; avoids the ~19 draws/book trap and tiny-triangle cost at distance (est. orders of magnitude vs per-book meshes). Cost: M. Risk: low-medium (readable titles at close range need a real texture path; LOD transition).
10. **Static-scene CPU hygiene + alpha-to-coverage foliage + `compileAsync` pre-warm.** Gain: `scene.matrixWorldAutoUpdate=false` with dynamic roots only, `frustumCulled=false` in bundles, pooled lights (cheap, removes per-frame walk and leaks); alpha-to-coverage removes `discard` on tiled GPUs (UNVERIFIED size); pre-warm removes 180-400 ms pipeline stalls at room entry. Cost: S-M. Risk: low (watch the `compileAsync` "Binding doesn't exist" bug #34632 in r186).

Near misses (not top 10): TRAA/TAAU (ghosting, velocity cost, conflicts with scaling); worker-hosted renderer (no GPU gain, no official WebGPU example); occlusion-query room proxies (async, outside bundles, probably unnecessary once portals exist); VXGI (expensive); FSR 2/3 port (compute-heavy); 30 fps cap as a user option (cheap, but a setting not a research item); hardware multi-draw-indirect (flagged, absent on phones).
